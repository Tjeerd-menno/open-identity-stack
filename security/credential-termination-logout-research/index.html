    Credential termination: downstream logout and audit research¶

    Archived pre-implementation baseline at 7abf59bc7951433ea821497ab919bd8aa4e4fbd5. See implementation and rollout for the subsequent changes.

    Research date: 2026-09-08. Scope: recommendation 2, follow-up findings F10–F12 and F17 from the assessment in the de8e checkout, checked against the current 8100 checkout. This is source and test inspection, not a runtime conformance result. No tests were run for this research. Source/test directories and the original assessment were secrets-scanned successfully before inspection.

    All four findings were open in the inspected baseline. Signed back-channel logout tokens and component tests exist, but the normal authorization flow does not provision downstream notification destinations; front-channel responses do not execute browser frames; the session-check page remains denied embedding; hintless logout still has no confirmation; and session termination still lacks durable actor audit.

    F10: downstream logout is not connected to ordinary authorization¶

    Normal authorization calls AddClientSessionCommand with only session and client identifiers (src/OpenIdentityStack.Api/Authentication/AuthorizationController.cs:160, :173). Although the command accepts both logout URIs (src/OpenIdentityStack.Application/Sessions/Commands/AddClientSessionCommand.cs:15), the use case ignores those parameters and only adds a client ID (:66). ClientSession.SetLogoutUris exists (src/OpenIdentityStack.Domain/Sessions/ClientSession.cs:79), but searching production source found no caller. Persistent columns exist (src/OpenIdentityStack.Infrastructure/Persistence/Sessions/UserSessionConfiguration.cs:78). They do not establish a provisioning path.

    Logout reads these nullable URIs from attached sessions (src/OpenIdentityStack.Application/Sessions/Commands/ProcessLogoutCommand.cs:76). The notifier skips missing back-channel destinations (src/OpenIdentityStack.Infrastructure/Identity/BackChannelLogoutNotifier.cs:49) and missing front-channel destinations (:101). Thus the normal inspected flow supplies no destination for either channel. The source search also found no production application registration fields named frontchannel_logout_uri or backchannel_logout_uri.

    Even if destinations are populated, the active front-channel URL generator sends sid without iss (src/OpenIdentityStack.Infrastructure/Identity/BackChannelLogoutNotifier.cs:108). The alternative service adds an issuer but hardcodes open-identity-stack (src/OpenIdentityStack.Infrastructure/Identity/FrontChannelLogoutService.cs:43); it is injected into the controller but never called there. The controller constructs DTOs named iframes and returns JSON or redirects immediately (src/OpenIdentityStack.Api/Authentication/LogoutController.cs:101, :114). Neither response causes the browser to request the RP logout frames.

    The back-channel factory is a useful existing building block: it chooses asymmetric signing credentials, sets issuer/audience and the session identifier, and resolves the configured or request issuer (src/OpenIdentityStack.Infrastructure/Identity/LogoutTokenFactory.cs:68, :79, :104, :123). The notifier posts a form containing logout_token (src/OpenIdentityStack.Infrastructure/Identity/BackChannelLogoutNotifier.cs:120). This proves token construction and an HTTP send path, not end-to-end RP termination.

    There is also a recovery gap: ProcessLogoutUseCase persists the logged-out session before notifying clients (src/OpenIdentityStack.Application/Sessions/Commands/ProcessLogoutCommand.cs:67, :73, :90). A repeat request returns a conflict for an already logged-out session (:61). The notifier correctly propagates caller cancellation (src/OpenIdentityStack.Infrastructure/Identity/BackChannelLogoutNotifier.cs:74), but that can leave later clients unattempted after persistence. Per-client failures are returned from the use case, while the HTTP controller reports successful logout without exposing notification outcomes (src/OpenIdentityStack.Api/Authentication/LogoutController.cs:106). Administrative logout similarly returns success with no delivery detail (:160). No persisted delivery job/outbox or resumable delivery path was found in this source inspection.

    Do not describe this as “no retries”: the API uses service defaults (src/OpenIdentityStack.Api/Program.cs:32) that install AddStandardResilienceHandler for HTTP clients (src/OpenIdentityStack.ServiceDefaults/Extensions.cs:29), and the notifier is registered with AddHttpClient (src/OpenIdentityStack.Infrastructure/ServiceCollectionExtensions.cs:213). Transient transport resilience does not establish durable recovery after cancellation, process exit, or prolonged RP outage. Exact effective retry behavior was not runtime-tested.

    Existing tests exercise mocked controller responses and isolated notification behavior. tests/OpenIdentityStack.Api.Tests/Authentication/FrontChannelLogoutTests.cs:45 asserts JSON frame descriptors, not browser requests. tests/OpenIdentityStack.Application.Tests/Sessions/AddClientSessionUseCaseTests.cs:60 exercises client association without URI provisioning. tests/OpenIdentityStack.Infrastructure.Tests/Identity/BackChannelLogoutNotifierTests.cs:73, :96, :352 cover HTTP failure, exceptions, and timeout classification; :347 asserts cancellation propagation. tests/OpenIdentityStack.Application.Tests/Sessions/SingleLogoutTests.cs:122 covers notification failure as a successful use-case result. These do not prove normal login → registered RP → logout → rejected retained RP cookie.

    Required acceptance evidence: create an RP through the supported registration path; authorize and establish an actual RP session; logout through the OP; observe signed back-channel POSTs and front-channel browser requests with the correct issuer/session identifiers before final redirect; verify the retained RP cookie is rejected. Exercise unreachable RPs, cancellation after local persistence, restart, repeated requests, and eventual delivery within an explicitly chosen deadline. Specify which channels can meet that deadline when no user browser is present.

    F11: session-check discovery contradicts response headers¶

    Discovery still advertises connect/check_session (src/OpenIdentityStack.Infrastructure/Identity/SessionManagementHandlers.cs:53). The Razor page exists (src/OpenIdentityStack.Api/Pages/Connect/CheckSession.cshtml:1), but its page model only exposes the cookie name (src/OpenIdentityStack.Api/Pages/Connect/CheckSession.cshtml.cs:6). The API applies global security headers (src/OpenIdentityStack.Api/Program.cs:167); middleware sets X-Frame-Options on every request (src/OpenIdentityStack.ServiceDefaults/SecurityHeadersExtensions.cs:36) and defaults it to DENY (:69). No session-check exception was found.

    Discovery metadata tests exist (tests/OpenIdentityStack.Infrastructure.Tests/Identity/SessionManagementHandlersTests.cs:22), but they do not load the advertised URL cross-origin in a browser. Acceptance must check real response headers and RP-origin embedding, validate session-state change messages, and preserve anti-framing protection on ordinary OP pages. Browser cookie restrictions also need explicit coverage. If the session-check profile is not intended to work, stop advertising it and document that capability decision.

    F12: hintless logout still terminates before any confirmation¶

    The anonymous GET/POST endpoint immediately signs out both cookies and deletes the session-management cookie (src/OpenIdentityStack.Api/Authentication/LogoutController.cs:51, :64). There is no user confirmation branch. The controller explicitly leaves validated id_token_hint initiation resolution deferred and always uses a null initiating-client ID (:86). It resolves the domain session only from existing principal sid/session_id claims (:167), with cookie/OpenIddict context fallback also explicitly deferred (:177). This is still application-level evidence of missing confirmation, not proof that arbitrary invalid requests bypass OpenIddict middleware validation.

    Controller tests supply a mocked OpenIddict request service (tests/OpenIdentityStack.Api.Tests/Authentication/LogoutControllerTests.cs:29) and directly exercise success, redirects, and frame DTOs (:45, :84, :115). They do not exercise real middleware plus a signed-in browser to establish hint validation or confirmation behavior.

    Add adversarial browser sequences first: hintless navigation must preserve authentication until consent; rejection/cancellation must retain it; a valid matching hint must follow the intended policy; mismatched, invalid, and expired hints must produce their documented validation/confirmation behavior; and state/registered redirects must survive only successful authorized completion. Test domain-session resolution with the real authentication pipeline rather than manually assigning claims.

    F17: no durable actor audit at the termination boundary¶

    ProcessLogoutUseCase depends only on the session repository, notifier, and clock (src/OpenIdentityStack.Application/Sessions/Commands/ProcessLogoutCommand.cs:31). The single-session revoker similarly has no audit dependency (src/OpenIdentityStack.Application/Sessions/Commands/RevokeSessionCommand.cs:38); revoke-all has repository/user-repository/clock dependencies and independently persists each revoked session (src/OpenIdentityStack.Application/Sessions/Commands/RevokeAllUserSessionsCommand.cs:42, :83). None of these inputs identify the acting administrator or self-service actor.

    The domain raises SessionRevokedEvent (src/OpenIdentityStack.Domain/Sessions/UserSession.cs:133), but production search found no consumer; the persistence mapping ignores DomainEvents (src/OpenIdentityStack.Infrastructure/Persistence/Sessions/UserSessionConfiguration.cs:108). This event is not durable actor audit. The existing AuditLogService already writes database entries and saves them (src/OpenIdentityStack.Infrastructure/Audit/AuditLogService.cs:41, :51), so a persistence mechanism is available, but these paths do not call it. Authorization on administrative logout does exist (src/OpenIdentityStack.Api/Authentication/LogoutController.cs:141); authorization alone does not establish auditability.

    Define durable actor, subject, session/grant scope, action, reason, outcome, timestamp, and correlation data at the shared termination boundary. Separate local invalidation outcome from RP delivery outcome, including later retries. Specify behavior if audit persistence fails and ensure records never contain tokens or cookie values. Add persisted-audit integration assertions for self logout, administrator logout/revoke, revoke-all, partial failure, and repeated requests; verify the actor is the authenticated caller rather than the affected user. Coordinate reset/disable/deletion audit with the core F06 termination contract rather than maintaining independent incompatible semantics.

    Recommended implementation order¶

    1. Establish the F06 credential invalidation contract and retained-credential sequence tests, including propagation deadlines and independent RP sessions.
    2. Build durable audit and delivery outcome semantics into that termination boundary; avoid adding notification calls to already separate mutation paths.
    3. Wire trusted application logout metadata into client-session association and add resumable back-channel delivery.
    4. Add protocol-aware logout confirmation/session resolution and actual front-channel browser completion.
    5. Fix or withdraw session-check advertising and verify it using a cross-origin browser test.

    Research validation: inspected implementation and test source only; no build, test suite, running stack, browser exercise, or certification plan was executed. The gaps above are source-backed; proposed acceptance scenarios remain to be implemented/run.
