# Credential boundary cutover

The coordinated cutover ends existing OpenID Provider sessions and grants. It is an operator action, never a routine seed step. Do not execute it in production until the integrated identity-boundary rehearsal and prerequisites are complete.

An authenticated human with current explicit unrestricted authority and actual authentication within five minutes calls `POST /api/admin/security/credential-cutovers`, sending `{"operationId":"<new UUID>"}` and `X-OIS-Administrative-Approval: acknowledge`. The dedicated administrative audience and approved client ceiling are required by the administrative boundary. Machines cannot approve cutover. Treat the operation identifier as an idempotency key and save it with the change record; it is not a credential.

The response records completion time and counts of revoked tokens, grants and sessions. A database transaction advances the singleton credential boundary, revokes OpenIddict records and local sessions, and writes the completed operation and audit event. Missing database state or failed authority reads fail closed. A revocation failure rolls back the boundary and mutations. If the response is lost after commit, authenticate again and retry the same identifier: the recorded result is returned without invalidating new credentials. An older operation identifier never restores an older boundary.

Each serving instance checks the durable boundary using an uncached scalar database query. Cookies and delegated credentials retain the identifier captured at authentication; refresh and cookie renewal cannot replace it with the current identifier. Existing authorization codes, refresh tokens, local API access tokens and supported provider token endpoints reject a mismatched boundary, including issuance that raced the cutover transaction. New client-credentials tokens capture the current boundary. Client authentication assertions are not OpenID Provider grants and remain subject to their normal validation rules.

The browser cookie must also name a current, active, unexpired local session for the active local user. Revoked sessions, including those revoked by email-trust withdrawal, require a fresh login. Management Web clears rejected credentials and requests `prompt=login` and `max_age=0`, retaining the return path. It does not retry a privileged mutation automatically after fresh login.

Apply schema changes before deploying code that reads the boundary. Drain older serving instances before the cutover; mixed binaries cannot enforce a shared new policy. Keep the boundary table, operation history, revocations and quarantine records in any rollback. Do not roll back to binaries that ignore these records or re-enable generic administrative audiences. A database restore from before cutover requires a new isolation and credential-invalidation plan before accepting traffic.

Independent business APIs validating a self-contained token without contacting this provider cannot be recalled by a provider database update. Inventory resource owners, accepted audiences, maximum access-token and ID-token lifetime, clock skew, validator caching, and the last possible issuance time. Coordinate resource-side rejection, introspection/deny-list enforcement, or wait out that bounded window before declaring those resources cut over. ID tokens already consumed by relying parties and their local sessions need relying-party action. The endpoint does not promise universal instant recall or formal OIDC certification.

Verification includes actual HTTP password, PKCE, token, approval and recovery flows; rejection of pre-cutover access/code/refresh credentials and cookies; durable reads across database contexts; retry after simulated revocation failure; and Management Web recovery. SQLite is used by these integration tests; PostgreSQL deployment rehearsal and external-resource windows remain explicit operational gates.
